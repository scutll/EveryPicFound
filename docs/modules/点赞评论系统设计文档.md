# 数据表结构

- 先只使用MySQL进行数据存储和读取，不考虑redis，高并发下数据库读取速度可能为瓶颈

## 评论表

- 评论功能分一级评论和评论下回复，回复分`一级评论回复`和`对其他用户回复`

```sql
CREATE TABLE picture_comment(
	picture_id BIGINT UNSIGNED NOT NULL COMMENT '图片id对应image-asset表中image_id',
    comment_id BIGINT NOT NULL AUTO_INCREMENT COMMENT '全局唯一评论ID',
    user_id BIGINT NOT NULL COMMENT '评论用户ID',
    
    root_comment_id BIGINT NULL COMMENT '(回复评论) 所属一级评论id, 若NULL则为一级评论',
    reply_user_id BIGINT NULL COMMENT '被回复用户ID, 一级评论或直接回复一级评论时为NULL',
    
    content VARCHAR(1000) NOT NULL COMMENT '评论内容',
    
    likes_count INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '点赞数',
    replies_count INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '回复数(包括直接和间接回复), 仅一级评论有效',
    
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    
    PRIMARY KEY (comment_id), 
    
    KEY idx_picture_root_time(
    	picture_id,
        root_comment_id,
        created_at,
        comment_id
    ),
    
    KEY idx_user_time(
    	user_id,
        created_at,
        comment_id
    )
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COMMENT = "图片评论区表";
```

其中`idx_picture_root_time` 可以用于**查询某张图片的一级评论**(`picture_id = ? AND root_comment_id IS NULL`)或者**某条一级评论下的回复**(`picture_id = ? AND root_comment_id = ?`)

然后`idx_user_time`可以用于**查询某用户最近评论了什么图片**

这里只保存评论回复的用户，并不保存回复具体回复了哪一条评论，在前端表现为 回复 `xxusername: `

## 用户点赞评论表

- 用于映射用户 - 评论 之间的点赞

```sql
CREATE TABLE picture_comment_like_user(
	comment_id BIGINT NOT NULL COMMENT '被点赞的评论ID',
    user_id BIGINT NOT NULL COMMENT '点赞用户ID',
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    
    PRIMARY KEY (comment_id, user_id),
    
    KEY idx_user_like_time(
    	user_id,
        created_at,
        comment_id
    ),
    
   	KEY idx_comment_like_time(
    	comment_id,
        created_at,
		user_id
    )
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COMMENT = '评论点赞用户表'
```

`PRIMARY KEY (comment_id, user_id)`可以保证(comment_id, user_id)元组全局唯一，但comment_id和user_id可重复出现，**防止同一用户对同一评论点赞**

`idx_user_like_time`可以**查询用户最近点赞了哪些评论**

`idx_comment_like_time`可以**查询该评论最近有什么用户点赞**

## 图片点赞表

- 跟评论点赞表类似，映射 图片id - 点赞用户id

```sql
CREATE TABLE picture_like_user(
	picture_id BIGINT UNSIGNED NOT NULL COMMENT '被点赞图片ID',
	user_id BIGINT NOT NULL COMMENT '点赞用户ID',
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    
    PRIMARY KEY (picture_id, user_id),
    
    KEY idx_user_like_time (
        user_id,
        created_at,
        picture_id
    ),

    KEY idx_picture_like_time (
        picture_id,
        created_at,
        user_id
    )
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COMMENT = '图片点赞用户表'
```

# 功能设计

- 评论区分为一级评论（直接在图片下进行评论）和回复评论（又分为回复一级评论和回复其他用户的回复评论）
- 在加载评论区时，加载第一页一级评论和一级评论下回复数<=3的所有回复评论，回复数>3的回复评论下在一级评论下折叠，后续用户点击后再进行加载
- 操作前先校验图片`picture_id`是否存在，

## 图片存在性跨服务校验

- `interaction-service`不直接访问`media-search-service`的图片资产数据库，而是通过图片存在性应用端口调用`media-search-service`提供的内部HTTP接口。
- 当前HTTP客户端使用Spring `RestClient`实现，调用`GET /internal/images/{pictureId}/exists`。调用时透传当前已认证用户的Bearer JWT，并配置连接超时和读取超时。
- 图片合法且不存在时，按图片不存在处理；网络异常、超时、下游非成功状态或响应格式不符合契约时，按图片资产服务不可用处理。

### 后续迁移到Feign

- 后续如果跨服务HTTP接口数量增加，或者需要统一使用声明式客户端，可以将当前`RestClient`适配器等价迁移为Spring Cloud OpenFeign。
- 迁移只替换基础设施层的HTTP客户端实现，图片存在性应用端口、`GET /internal/images/{pictureId}/exists`接口契约和上层业务流程保持不变。
- Feign实现必须继续保留当前Bearer JWT透传、连接与读取超时、响应内容校验，以及下游失败的异常转换语义。
- 迁移到Feign本身不代表引入服务注册与发现、客户端负载均衡、重试、熔断或降级；这些能力不在本次迁移范围内，需要后续按实际需求单独设计。

## 评论区功能

### 发布一级评论

之后数据库插入:

```sql
INSERT INTO picture_comment (
    picture_id,
    comment_id,
    user_id,
    root_comment_id,
    reply_user_id,
    content
)
VALUES (?, ?, ?, NULL, NULL, ?)
```

### 回复一级评论

需要完成两个数据库操作：插入评论和一级评论replies_count + 1

```sql
开始事务

1. 查询 root_comment_id 对应的一级评论
2. 校验一级评论存在
3. 校验一级评论属于当前 picture_id
4. 校验该评论的 root_comment_id IS NULL
5. 插入回复记录
6. 一级评论 replies_count 原子加 1

提交事务
```

### 回复评论下的其他用户回复

`root_comment_id = 一级评论comment_id, reply_user_id = 被回复用户id, replies_count + 1`

也是需要进行两个数据库操作

```
开始事务

1. 校验 root_comment_id 对应的一级评论存在
2. 校验一级评论属于当前 picture_id
3. 校验 root_comment_id 对应记录确实是一级评论
4. 校验 reply_user_id 对应用户有效
5. 插入回复记录
6. 一级评论 replies_count 原子加 1

提交事务
```



### 加载图片评论区

- 先查一级评论，若replies_count <= 3 则把回复也查出来

第一步分页查询一级评论：

```sql
SELECT
    picture_id,
    comment_id,
    user_id,
    root_comment_id,
    reply_user_id,
    content,
    likes_count,
    replies_count,
    created_at
FROM picture_comment
WHERE picture_id = ?
AND root_comment_id IS NULL
ORDER BY created_at DESC, comment_id DESC
LIMIT ?
```

第一次请求没有游标

后续后端将本页最后一条一级评论的`created_at`和`comment_id`返回生成下一页起始游标返回给前端时再查询：

```sql
WHERE picture_id = ?
AND root_comment_id IS NULL
AND (
    created_at < #{cursorTime}
    OR (
        created_at = #{cursorTime}
        AND comment_id < #{cursorId}
    )
)
ORDER BY created_at DESC, comment_id DESC
LIMIT ?
```

然后遍历一级评论：

```
if replies_count = 0：
    不查询回复

if 1 <= replies_count <= 3：
    查询该一级评论下全部回复

if replies_count > 3：
    默认不查询回复，，前端根据replies_count显示展开入口 `展开{replies_count}条回复`
```

查询某一级评论下回复：

```sql
SELECT
    picture_id,
    comment_id,
    user_id,
    root_comment_id,
    reply_user_id,
    content,
    likes_count,
    replies_count,
    created_at
FROM picture_comment
WHERE picture_id = ?
  AND root_comment_id = ?
ORDER BY created_at ASC, comment_id ASC;
```



### 展开一级评论下回复

- 用`picture_id + root_comment_id`查

```sql
SELECT
    picture_id,
    comment_id,
    user_id,
    root_comment_id,
    reply_user_id,
    content,
    likes_count,
    replies_count,
    created_at
FROM picture_comment
WHERE picture_id = ?
  AND root_comment_id = ?
ORDER BY created_at ASC, comment_id ASC;
```

查询之前需要先校验root_comment_id对应评论存在，picture_id存在一级该评论是一级评论等信息

可以使用`created_at + comment_id`进行分页查询

### 点赞评论

点赞需要同时完成：

```
1. 插入用户与评论的点赞关系
2. 评论 likes_count + 1
```

```
MySQL事务:

1. 校验评论存在
2. 插入点赞关系
3. 评论 likes_count 原子加 1

提交事务
```

插入点赞关系:

```sql
INSERT INTO picture_comment_like_user(
	comment_id,
	user_id
)
VALUES (?, ?);
```

使用`PRIMARY KEY (comment_id, user_id)` 阻止同一用户重复点赞同一评论

更新点赞数

```sql
UPDATE picture_comment
SET likes_count  = likes_count + 1
WHERE comment_id = ?
```

### 取消点赞

需要完成事务：

```
1. 删除点赞关系
2. 评论 likes_count - 1
```

事务流程

```
开始事务

1. 删除点赞关系
2. 检查删除影响行数
3. 只有删除成功时，评论 likes_count 减 1

提交事务
```

删除点赞关系:

```sql
DELETE FROM picture_comment_like_user
WHERE comment_id = ?
	AND user_id = ?;
```

当`DELETE`影响行数为1时，才允许执行下一步事务

点赞数减少

```sql
UPDATE picture_comment
SET likes_count = likes_count - 1
WHERE comment_id = ?
	AND likes_count > 0;
```

影响行数也为一，事务成功，否则回滚

### 查看自己最近点赞的评论

查询点赞记录 + 展示评论内容、评论作者和所属图片：

```sql
SELECT
	l.comment_id,
	l.created_at AS liked_at,
	c.picture_id,
	c.user_id AS comment_user_id,
	c.content,
	c.likes_count,
	c.replies_count,
	c.created_at AS comment_created_at
FROM picture_comment_like_user l
LEFT JOIN picture_comment c
	ON c.comment_id = l.comment_id
WHERE l.user_id = ?
ORDER BY liked_at DESC, l.comment_id DESC
LIMIT ?;
```

深分页时使用 `liked_at + comment_id`作为游标

- 这里需要使用`LEFT JOIN`，当`picture_comment_like_user`表里有点赞记录但`picture_comment`中无（评论以删除但点赞记录较多可能不删除或者异步消化）,这时候会返回评论表信息为NULL
  - 若使用`JOIN(INNER)`，则不能返回任何记录，因为INNER JOIN只返回两个表里面都有的记录

### 查看自己最近评论

只需插入

    picture_id,

)

```sql
DELETE FROM picture_like_user
WHERE picture_id = ?
	AND user_id = ?;
```

使用COUNT查询，因为图片表中还没有点赞数字段

SELECT COUNT(*)

## 扩展说明

- 后续要开放评论删除功能时，不仅要删除评论表中的评论，还需要删除点赞表中若干记录，这些删除工作可以交由MQ异步消化，特别是后者。或者如果点赞表中不立即删除，可以在用户查询自己最近点赞的评论的时候显示“该评论已删除”，后续再慢慢处理点赞表数据
- 前端可不将用户信息附加在评论/点赞请求中，而在认证板块附带token时候进行鉴权和用户信息查询

- 点赞方面：图片表后续可增加 likes_count，但当前可以继续 COUNT。
  - 高并发点赞可使用 Redis Set 保存点赞用户 + 后续批量同步MySQL 的策略
    - 派生计数可以接受暂时不准确
    - 不要求绝对一致，但必须有重试、脏数据扫描和定期校准。
    - Redis Lua 同时修改点赞状态、计数和 Stream/脏数据标记。
  - 评论正文仍同步持久化，点赞数和回复数可以最终一致。
- 检测到热门评论数据先放redis，低峰时再回库
- 使用mq队列保证同一用户持续点赞 - 取消 动作不乱序

- 评论区使用增量轮询（前端），定期更新评论区内容

- 评论区用户资料获取 user_id 后去重，只需一次批量查询。
