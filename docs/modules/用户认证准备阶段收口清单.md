# 用户与认证准备阶段收口清单

本文记录微服务基础阶段与用户认证首个编码切片之间的边界，防止为了“提前准备”而过早引入业务模型、基础设施对象或未确认的技术方案。

## 已完成的基础边界

- 根 Maven Reactor 已包含 `security-contract`、`identity-service`、`media-search-service` 与 `gateway-service`。
- `identity-service` 为 Spring MVC 服务，`gateway-service` 为 Spring Cloud Gateway WebFlux 服务，`media-search-service` 保持 MVC 资源服务职责。
- Java 17、Spring Boot、Spring Cloud、MyBatis-Plus 与 Maven Enforcer 的基础版本约束已建立。
- `security-contract` 只承载跨服务使用的 JWT Claim、Scope 与必要内部 DTO；不得放入 PO、Mapper、Repository、领域聚合或 Redis 实现。
- Identity、Gateway 与 Media 已建立分层包边界；尚未把包骨架当成业务实现完成。
- Docker Compose 已定义 MySQL、Redis、Qdrant、RocketMQ 与三个 Java 服务的容器边界；本阶段不要求启动或验证它们。
- Gateway 的 `/api/auth/**` 认证服务路由覆盖 `/api/auth/sessions/**`；已移除错误且重复的 `/api/sessions/**` 路由。

## 本阶段明确不做的事情

- 不创建 `user_account`、`user_session`、`user_refresh_token` 或 `outbox_event`。
- 不创建 Redis 认证状态、登录保护、屏障、deny Key 或 Lua 脚本。
- 不生成 RSA 私钥、公钥、`kid`、Refresh Token Pepper 或生产环境密码。
- 不创建 RocketMQ Topic、Consumer Group 或业务事件。
- 不为 Outbox 预先锁定 Debezium CDC、应用轮询 Relay 或其他消息中继实现。
- 不为了准备阶段修复旧测试、执行全量构建或启动 Docker。

## 首个编码切片：I-01 用户注册

I-01 的目标是只形成“注册写入账户”的可测试闭环。注册成功不创建 Session、Refresh Token、认证状态缓存、Outbox 或消息事件。

开始 I-01 前的信息结构与技术选择已经完成确认，权威记录见《EveryPicFound 用户与认证模块编码计划》的 D01～D33：

1. 用户 ID 使用有符号 MySQL `BIGINT AUTO_INCREMENT`。
2. 用户名、昵称和密码输入规则及大小写语义已经锁定。
3. 密码使用 BCrypt，并以 `DelegatingPasswordEncoder` 的 `{bcrypt}<哈希>` 格式保存；工作因子在编码切片实测。
4. 数据库变更使用 Flyway 管理版本化 SQL。
5. `user_account` 字段、空值、索引、`CHECK`、状态与 UTC 时间语义已经锁定。
6. 注册与登录保持独立；前端注册成功后复用内存凭据调用登录，注册接口不创建登录态。

I-01 现在可以按需引入首次实际使用的 Flyway、MySQL/MyBatis 与密码编码依赖，并创建对应迁移、Repository、领域规则、接口与测试。依赖仍须在首次使用时逐项引入，不一次性补齐后续认证依赖。

## 后续技术决策门

| 首次使用场景 | 需要先确认的事项 |
| --- | --- |
| JWT / Token 基础能力 | 已确认 RS256、RSA 2048 位、PKCS#8 私钥、X.509 公钥、Access 30 分钟、Refresh 1 小时、Session 1 天和 Clock Skew 30 秒；`kid`、密钥轮换、Refresh 滑动语义、Cookie 与 CSRF/Origin 策略仍在对应切片确认 |
| 用户登录 | Session 与 Refresh Token 完整字段、登录保护阈值、Redis Key 与 Lua 行为 |
| 内部认证状态查询 | Gateway 到 Identity 的内部信任方式：内网隔离、内部凭证或 mTLS/签名 |
| Refresh Token 重放 / 退出 | Outbox Relay 方案、RocketMQ 客户端、Topic、Consumer Group、重试与幂等语义 |
| 采用 Debezium CDC | 先补充两篇设计文档中的 CDC、Binlog、RocketMQ Sink、重复投递与恢复机制，再决定是否实施 |

RocketMQ 是已确认的消息队列；未确认的是 Outbox 到 RocketMQ 的中继方式。当前 Compose 中的 Debezium 配置仅作为候选实验配置，不能替代技术决策与文档补充。

## 编码协作约定

每个功能切片遵循：

```text
确认数据变化与技术选择
→ 你实现核心配置、事务、SQL、Redis/Lua、MQ 与关键测试
→ Codex 生成 DTO/PO/Converter/Fixture 等重复代码
→ 运行目标测试与故障场景
→ 观察日志、指标和基础设施状态
→ 复盘 Linux 命令与 Git 提交
```

新功能采用目标测试优先策略；旧测试是否迁移、替换或删除，作为独立清理任务处理，不阻塞首个业务切片。
