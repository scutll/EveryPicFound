# EveryPicFound 文档索引与维护规范

本目录保存项目开发、技术学习和验证过程中需要长期维护的资料。文档应帮助读者快速回答三个问题：

1. 当前项目实际采用什么方案？
2. 为什么这样选择，约束和验证依据是什么？
3. 相关技术本身如何工作，去哪里继续深入？

## 目录分类

| 目录 | 内容职责 | 不应包含 |
| --- | --- | --- |
| [`project/`](project/) | PRD、系统架构、全局模块关系、公共数据与接口等跨模块当前事实 | 单个模块的实现过程、通用工具教程 |
| [`modules/`](modules/) | 业务模块的具体设计、选型理由、项目内工具用法、编码规范、计划与工作记录 | 可脱离项目阅读的完整技术原理 |
| [`technologies/`](technologies/) | RocketMQ、Redis、MySQL、Spring Security、Linux、Git 等通用技术分析 | EveryPicFound 专用 Topic、参数和业务契约 |
| [`reports/`](reports/) | 压测、实验、故障演练和方案对比的环境、过程、数据与结论 | 未经验证的设计结论、通用技术教程 |

第一层目录保持稳定；只有真实文档数量增加、出现明确独立主题时，才在对应目录下增加子目录。不要预先建立空的多层目录。

## 业务文档与技术文档的边界

- 业务模块文档回答“EveryPicFound 在这里怎样使用这项技术，以及为什么这样使用”。
- 技术分析文档回答“这项技术通常具备什么能力、如何工作、怎样使用和排障”。
- 同一知识点只保留一份完整说明。业务文档记录项目结论并链接技术分析；技术分析不复制项目专用配置。
- 示例：用户认证模块记录实际 Topic、Tag、消息契约和重试约束；RocketMQ 技术文档介绍 NameServer、Broker、投递语义和通用客户端用法。

## 何时需要记录或更新文档

任务出现以下任一变化时，应检查相关文档：

- 技术选型、替代方案或依赖发生变化。
- 参数值、默认值、选择依据或容量假设得到确认。
- API、数据模型、缓存结构、消息契约、事务边界或并发规则发生变化。
- 形成新的编码规范、配置方式、工具命令、测试方法或排障流程。
- 压测、实验、故障演练产生了需要保留的环境、数据和结论。
- 实现结果证明旧文档存在错误、遗漏或已经失效。
- 一个编码切片结束，需要记录关键修改、验证证据、命令和遗留问题。

代码或配置使旧文档失效时，文档更新属于当前任务完成条件，不能留待不确定的后续任务。

## 新增还是更新

优先更新现有权威文档。只有满足以下条件之一时才新建文档：

- 内容回答了一个可以独立检索的新问题。
- 内容的更新周期或读者与现有文档明显不同。
- 通用技术说明已经影响多个业务模块，继续放在单一模块中会造成重复。
- 测试或实验需要独立保留环境、版本、步骤和原始结果。

新增或大幅调整文档前，先与用户确认：记录范围、目标目录、更新现有文档还是新建文档，以及哪些内容只应通过链接引用。

## 单篇文档的精简结构

每篇文档只回答一个核心问题，标题应让读者无需打开正文也能判断内容。推荐按需使用以下结构，不要求机械填满：

1. **摘要**：当前结论、适用范围和阅读收益。
2. **背景与约束**：为什么需要解决这个问题。
3. **方案或原理**：核心流程、组件职责和关键细节。
4. **选择依据**：候选方案、参数理由和取舍。
5. **使用与编码**：关键配置、代码入口、命令及注意事项。
6. **验证与观测**：测试方式、预期结果、指标和故障表现。
7. **边界与风险**：不适用场景、已知限制和后续条件。
8. **关联资料**：项目内权威文档链接。

控制长度时遵循：

- 结论放在前面，历史过程只保留会影响理解和复盘的部分。
- 表格用于固定字段和方案对比，流程图只用于单靠文字难以表达的关系。
- 不重复粘贴大段代码；保留关键片段并链接实际代码入口。
- 不为完整而罗列与当前主题无关的工具能力。
- 当一篇文档开始回答多个可独立检索的问题，或不同部分需要独立更新时，再拆分文档。

## 工作记录与知识提炼

每个编码切片只记录简短工作记录：

- 目标与范围。
- 关键决策及理由。
- 实际修改和验证证据。
- 使用的测试、Linux、Git 或基础设施命令。
- 失败现象、原因和修正。
- 遗留问题及触发条件。

工作记录中的内容满足“可脱离当前业务复用”时，再提炼到 `technologies/`；属于模块当前约束时，更新 `modules/` 中的设计或规范；属于客观测试数据时，写入 `reports/`。提炼后在工作记录中保留简短结论和链接，不复制全文。

## 文档维护流程

1. 开始任务前阅读本索引，再读取相关分类索引和权威文档。
2. 修改前识别哪些现有结论会被影响，并与用户确认记录范围。
3. 实现过程中保留关键选择、验证命令和证据，不记录密码、Token、Cookie 或真实密钥。
4. 收口时更新权威文档；有必要时新增工作记录、技术分析或报告。
5. 检查相对链接、文件职责、重复内容和过时结论。
6. 在 Git 差异中同时审查代码与文档是否一致。

## 状态与废弃

- 默认文档表示当前有效；尚未确认的内容必须明确标记为“草案”或“待决策”。
- 局部结论失效时直接更新正文，并通过 Git 历史追溯旧版本。
- 整篇文档被替代时，在开头标记“已废弃”、说明原因并链接替代文档；真正出现此类文档时再建立归档目录。
- 迁移文档时保留原文件名，先修复所有引用；是否改名作为独立任务处理。
- 本地若存在被 `.gitignore` 排除的 `docs/outdated/`，其内容属于未纳入仓库维护的历史或课程资料，不计入本文档体系；除非用户明确要求，不迁移、不更新也不建立索引。
